# HLA Agent Validation & Governance Guide

This document defines the production-facing validation and governance standard for this project.

## 1) Two-Phase Evaluation Model

### Phase 1: Tradeoff Selection (No Diagram Generation)
- Purpose: Select the best architecture pattern candidate using deterministic gates.
- Inputs: FRs, NFRs, architecture candidates generated by LLMs.
- Scoring:
  - `RCR = covered_FRs / total_FRs`
  - `NAS = average(nfr_support_scores)` from a deterministic evidence rubric (heuristic)
  - `Phase1CAS = 0.50*RCR + 0.50*NAS`
- Output: Ranked candidates, quality-attribute tradeoff decision context, manual candidate selection.
- Iteration: Manual only, max 2 reruns per candidate.

### Phase 2: HLD Structural Validation + Diagram Generation
- Purpose: Validate selected architecture quality and generate HLD artifacts.
- Scoring:
  - `CAS = 0.25*RCR + 0.25*NAS + 0.20*SMI + 0.15*LSCS + 0.15*SCI`
- Output artifacts:
  - Winner JSON
  - Evaluation report
  - PlantUML diagram
  - Mermaid diagram
  - Phase-2 radar chart (5 metrics)

## 2) Why Validation Is Deterministic (Not LLM-Judged)

Industry reviews favor deterministic scoring for:
- Repeatability: same input -> same score
- Auditability: evidence and formula can be reviewed line-by-line
- Governance: easier to defend during architecture and compliance reviews
- Drift control: avoids model-to-model and run-to-run judge variance

LLMs are used for generation, not for final numeric validation.

Note on "industry validity":
- Deterministic scoring improves auditability and repeatability.
- However, the numeric coefficients used by NAS are **project parameters**.
- Do not claim NAS is a standardized or academically proven metric unless you calibrate
  and benchmark it against expert judgments and/or operational outcomes.

## 3) Metrics and Pattern Coverage

All metrics are designed to evaluate architectures generated from these patterns:
- Layered Architecture
- Event-Driven Architecture
- Microkernel Architecture
- Microservices Architecture
- Space-Based Architecture

### Metric Summary
- RCR: Functional coverage feasibility gate.
- NAS: Deterministic NFR evidence rubric based on explicit mechanisms, interaction types, and style modifiers.
- SMI: Martin instability-based modularity signal.
- LSCS: Style-aware topological consistency checks for all five patterns.
- SCI: Structural naming and responsibility clarity.

## 4) Architecture Review Compatibility Notes

This system is compatible with established architecture review intent:
- Uses FRs and quality-attribute-oriented evidence.
- Emphasizes tradeoff-focused candidate selection.
- Preserves a manual decision point before HLD elaboration.

Relationship to common standards/frameworks:
- ATAM: NAS supports ATAM-style discussions by making quality-attribute evidence explicit, but ATAM does not define NAS's numeric formula.
- ISO/IEC 25010: NAS NFR categories can be mapped to ISO/IEC 25010 quality characteristics; ISO/IEC 25010 does not define NAS's numeric formula.

For full ATAM audits, attach run artifacts externally:
- Utility tree
- Key quality scenarios
- Sensitivity points
- Tradeoff points
- Risk/non-risk register

## 5) Frontend Transparency Requirement

The UI exposes complete per-candidate LLM generation logs:
- provider
- duration
- per-attempt status
- raw generated output

This ensures traceability from generated candidate to deterministic validation result.
